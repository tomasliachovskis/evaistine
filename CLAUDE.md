# eVaistine.lt

Price comparison for Lithuanian pharmacies only (https://evaistine.lt/, brand written `eVaistine.lt`): non-prescription medicines, vitamins and supplements, cosmetics, hygiene, mother-and-baby and medical goods. It's a fork of the superakcijos.lt grocery aggregator (`/Users/tomas/www/nuolaidos`, the git remote `upstream`), so most of the code, and the lessons below, come from groceries. Project decisions (stores, categories, palette, logo, schema, safety) live in `docs/evaistine.md`. The superakcijos SEO/GSC/keyword research is in `docs/superakcijos-legacy/`, about groceries and not this site.

## Blade frontend: reuse styles across pages, don't reinvent them per page

The Blade views (`resources/views/`) were ported from the Next.js app's React components one page at a time, and that porting process flattened several shared React components (a discount-percent badge, a store-logo pattern, count pills) into copy-pasted, slightly-different Tailwind class strings at each call site instead of one reusable Blade component — an audit found 4 near-duplicate discount-badge implementations, 9 divergent store-logo sizings, and 16 distinct arbitrary `text-[Npx]` values doing jobs the standard `text-xs/sm/base/lg` scale already covers.

- **Before writing a new UI pattern (badge, pill, card, icon treatment), check `resources/views/components/` for an existing one first** — `discount-badge.blade.php`, `count-pill.blade.php`, `store-logo.blade.php`, `favorite-button.blade.php`, `store-subscribe-button.blade.php` already cover the most common cases. If you're about to copy-paste a `class="..."` string from another file, extract a shared component instead (same pattern as those five).
- **The site is designed for older readers (see `docs/ui-older-readers.md`).** The Tailwind type scale is shifted up one step in `app.css`, so `text-xs` is 16px and body text is 18px. Controls are 48px at least (`min-h-12`) and carry a word next to the icon. Filled buttons use `bg-action` (navy), text links `text-dark-green` (navy; the token names are left over from superakcijos' green). Discount badges use `bg-deal text-deal-foreground` (raspberry), never a hardcoded color. Popups use the `.sheet-*` classes plus `x-back-closes`, and sticky bars use `var(--header-h)`. Check new UI with the 390px/1440px audit described there.
- **Prefer standard Tailwind size classes (`text-xs`/`text-sm`/`text-base`/`text-lg`, `size-4`/`size-5`/`size-6`) over arbitrary `text-[Npx]`/`size-[Npx]` values.** The one sanctioned exception is hero price numbers, which get named tokens (`text-price-lg`/`text-price-hero` in `resources/css/app.css`'s `@theme` block) instead of a standard label size, because they're display numbers, not label text.
- **When unifying sizes across pages, verify each call site's actual semantics before forcing it into the shared shape** — two things that look like the same component can have different rules. Found this session: a store's "iki X%" badge on the keyword page always shows the real max discount, while the product page's promo badge only shows above 20% — routing the first through the thresholded `<x-discount-badge>` would have silently hidden it below 20%. And a "chip list" of many wrapped store/city tags is a different UI role from a small set of prominent nav-tab buttons, even though both are "bordered pills" — forcing the chip list into the heavier nav-tab shape made it visually worse, not more consistent.

## Adding a new store (end-to-end checklist)

Written on superakcijos while onboarding Gulbelė, Vynoteka, Thomas Philipps and Ermitažas; the store examples below are those grocery stores, the rules apply to pharmacies the same way. Do these in order — later steps depend on earlier ones.

### 1. Backend: register the store

1. Add a migration that inserts into `stores` (copy an existing one, e.g. `database/migrations/2026_06_16_120000_add_gulbele_store.php`): sets `name` + `slug` only. Check for an existing row by slug first (idempotent `up()`), and delete-by-slug in `down()`. Run with `sail artisan migrate`. All seven pharmacy chains already exist.
2. Price/discount parsing: every store goes through the single `App\Rules\StoreRules\DefaultRules` (the per-store classes were all empty passthroughs and were removed). Only add per-store handling if a store's raw price/discount strings genuinely need it.
3. Add the store name => scraper filename to `config/scrapers.php` (e-shop) or `config/flyer_scrapers.php` (leaflets); `scrapers:run`/`flyers:scrape` read those maps. Add a main chain to `config('stores.main_slugs')` if it should sort first.

### 2. Write the scraper (`scrapers/{store}.js`)

- Scrapers are standalone Node/Puppeteer scripts (`puppeteer-extra` + stealth plugin), not PHP — invoked as `node scrapers/{store}.js`, POSTing scraped rows to this app's own `POST /api/scrapers` endpoint (`http://127.0.0.1/api/scrapers`) as a plain array of objects with keys from `DiscountTemp`'s fillable: `name, category, product_url, store, original_price, discounted_price, discount_percent, condition, card, start_at, end_at, info, brand, image_url`. `store` must match the `stores.name` string (matched case-insensitively downstream).
- **Before writing selectors, actually render the target page with a throwaway Puppeteer script and inspect the real DOM** — do not guess selectors from viewing raw HTML/curl output. Concretely check for:
  - **Lazy-loaded/virtualized lists**: some sites only render a fraction of a page's cards until scrolled (Vynoteka rendered ~7 of 20 cards until scrolled — missed ~65% of products silently). Scroll-and-wait-until-stable before reading cards on every page.
  - **Fake pagination overflow**: requesting a page number past the last one may silently re-render page 1's content instead of an empty result (seen on Vynoteka). Relying on "0 cards found" to stop paginating can loop forever — compare each page's card URLs against page 1's and stop on a repeat, or find a genuine total-page count in the DOM.
  - **Cookie consent dialogs** (commonly Cybot Cookiebot — `#CybotCookiebotDialogBodyLevelButtonLevelOptinAllowAll`) must be dismissed once before scraping, matching the exact button text/id (don't guess "Accept"/"priimti" — read the actual button).
  - **Where discount validity dates come from**: per-product page JSON (e.g. Gulbelė's `data-product="{...}"` `specific_prices.from/to`), a sitewide "current leaflet" link/page with dates embedded in a URL slug (Vynoteka's `/nr-N-kainos-galioja-YYYY-MM-DD-YYYY-MM-DD`) or as plain text on that page (Thomas Philipps' `/leidinys` page: "Savaitės pasiūlymai 2026.08.17–08.23", a partial end-date sharing the start's year/month), or explicit "Galioja nuo X iki Y" text on the card. `discounts:process` **silently drops any row where both `start_at` and `end_at` end up null** — always find a real source for at least one date.
  - **Plain server-rendered sites need no Puppeteer scrolling/JS-wait tricks** (Thomas Philipps: a WordPress site, prices/discounts already present in the raw HTML, `curl` alone was enough to inspect it) — but still launch it the same way as every other scraper for consistency; just skip the scroll-until-stable step.
  - **Listing pages sometimes only expose a coarse top-level category** (e.g. Thomas Philipps' `/maisto-prekes` page only says "Maisto prekės", not the real subcategory). If the site's own *product* pages carry a more specific breadcrumb (e.g. `Pagrindinis > Maisto prekės > Šokoladai`), fetch each scraped product's own page (plain `fetch()`, batched like Gulbelė's `enrichProduct`, no need for a full Puppeteer navigation if the site doesn't need JS rendering) and take the last 2 breadcrumb entries *before* the product-name entry, joined with `/` (e.g. `Maisto prekės/Šokoladai`) — this reuses `resolveCategoryId()`'s existing slash-hierarchy matching instead of inventing a new category shape.
- **Pharmacy e-shop scrapers collect the full catalog by default.** The site compares the same product across pharmacies, which needs every price, not just the ones on sale. On superakcijos, assuming discount-only was wrong twice (Vynoteka, Thomas Philipps): "rinkti prekes"/"prekes imam" means the full catalog; build discount-only only when the request says "nuolaidas"/"akcijas". Non-discounted rows still need `discounted_price` (the current shown price) but leave `original_price`/`discount_percent` empty — `DefaultRules::validate()` only requires `discounted_price > 0`.
- **Stores that publish no validity dates at all** (Ermitažas: nothing on the card or product page): use the current Monday–Sunday week as `start_at`/`end_at` (see `currentWeek()` in `scrapers/ermitazas.js`). Don't leave `end_at` null — `discounts:archive-expired` deletes null-`end_at` rows once `updated_at` is a day old, and `discounts:process` never touches an already-existing `Discount`, so they'd vanish the day after every run. Don't use a rolling "today" date either — each day's run would create a second overlapping row per product.
- **Take the category string from the listing page, not the product's own category field, when the product field can hold several categories.** Ermitažas' product `category[]` is several category paths flattened into one array, so its tail sometimes lands in an unrelated category we deliberately skip (hair clippers from "Buitinė technika" on a dog-hygiene item). The listing page's own `breadcrumbs` are always the curated category being scraped.
- **Send `ean` when the store publishes a barcode** (Ermitažas `barcode[]`). `discounts:process` matches a product by EAN before name/slug matching and stores it on `products.ean`. Only send a real retail barcode: `ProcessDiscounts::normalizeEan()` rejects multipack codes with a suffix (`4779017040533BLK`) and in-store EAN-13s (prefix `2`), and the scraper should drop them too. A value over 14 characters makes the whole POST batch fail with a 500 partway through, leaving a partial batch in `discount_temp`.
- **Scrapers POST to the local API** (`http://localhost/api/scrapers`) by default. Newer scrapers read `SCRAPER_API_URL`; set it inside the container, as `sail bash -c 'SCRAPER_API_URL=... node scrapers/{store}.js'`. A plain `VAR=x sail ...` prefix never reaches the container.
- **Send `ean` for pharmacy products whenever the site has it** (Eurovaistinė: `sku`). Cross-pharmacy matching relies on it, since names for the same medicine differ a lot between chains (strength, `N20`, form).
- **Yumpu leaflets (Eurovaistinė, Apotheka) are behind AWS WAF since 2026-10.** Don't fetch `yumpu.com/.../document/json` directly or open the embed URL: both get 403 even in stealth Chrome. Open the pharmacy's own leaflet page in stealth Chrome and catch the iframe's `document/json` response (`fetchYumpuDocumentViaPage()` in `scrapers/flyers/_shared.js`); the page images then download with a plain fetch.
- **Cloudflare-challenged sites (Senukai, tried 2026-09-24) aren't scrapable from the Sail container's headless Chrome.** The homepage passes, but every `/c/...` category URL (via `page.goto` or in-page `fetch`) stays on "Just a moment..." with a 403, even with stealth, a matching Chrome UA and viewport. Dropped for now. A real browser (Claude-in-Chrome) passes fine, so the block is on the headless fingerprint.
- Test manually before wiring into the flow: `node scrapers/{store}.js`, then check `DiscountTemp::where('store', '{Store}')->count()` roughly matches the real site's product/offer count. Don't trust a low number without cross-checking the real page — investigate before assuming it's "just how many are on sale." Also don't trust a single run's total at face value if the scraper doesn't retry on a failed page load — a single transient timeout mid-category can silently truncate that category's pagination (happened on Thomas Philipps: one flaky page load cut one category from 11 pages down to 3). Retry a few times before concluding a page has no more products.

### 3. Category mapping

- `resolveCategoryId()` (in `ProcessDiscounts.php`) resolves a scraped category string to a `Category` via `category_mappers`. On first run, every one of a new store's distinct category strings that can't be resolved lands in `category_mappers` with `category_id = null` — expected, not a bug.
- **Rule: `category_mappers.category_id` and `products.category_id` must ONLY ever point to a root category (`parent_id IS NULL`), never a subcategory.** Confirmed on superakcijos by data (661/664 mappings root-only) and by direct user correction. The planned pharmacy roots are listed in `docs/evaistine.md`; ailments are a separate layer, not subcategories. Before setting either field, walk `parent_id` up to the root if the target category isn't already one.
- Run `sail artisan categories:map-mappers` (dry-run first with `--dry-run`) to dedupe `category_mappers` rows and auto-map remaining unmapped ones to a root category via GPT. It correctly leaves genuinely-too-generic labels (e.g. "Visos prekės") unresolved for manual review.
- `sail artisan categories:bulk-map` is a **different, older mechanism** — it GPT-classifies `discount_temp.category` text directly (not `category_mappers`), name-matching against an existing `Product` first and only falling back to GPT when no match exists. Its no-argument default used to loop a hardcoded 13-store list that silently missed any store not on it (confirmed live 2026-09-11: Promo Cash&Carry and Thomas Philipps were never in it, so their blank-category rows could never resolve, ever, independent of OpenAI's own availability) — it now queries for whoever actually has pending blank-category `discount_temp` rows, so a new store is covered automatically. Call it with an explicit store argument (`categories:bulk-map {store}`) to run it for just one store.
- **Important gotcha**: `discounts:process` marks a `discount_temp` row `processed = true` even when its category is still unmapped (no `Discount`/`Product` gets created for it). Mapping the category afterward does **not** retroactively reprocess it — `Product::firstOrCreate` inside `processTempDiscount()` only sets `category_id` when a product is newly created, never on an existing row. After mapping new categories, find affected rows and flip them back to `processed = false` before re-running `discounts:process`:
  ```php
  $discountedUrls = Discount::where('store_id', $store->id)->pluck('product_url');
  DiscountTemp::where('store', '{Store}')->whereNotIn('product_url', $discountedUrls)->update(['processed' => false]);
  ```
  Then `sail artisan discounts:process` again. If the resulting `Discount` count is well below the scraped row count, this is almost always why — check before assuming data loss.
- **Another gotcha — coarse mappers shadow granular ones**: if a coarse category string (e.g. "Maisto prekės") already has a *mapped* `category_mappers` row, `resolveCategoryId()`'s slash-split logic will match it via the first-part fallback *before* ever falling through to create a mapper for a more specific "Category/Subcategory" string — so no unmapped row for the specific combo ever gets created, and every product silently inherits the coarse category forever. If you add per-product subcategory enrichment (previous section) after already having a coarse mapper in place, delete the coarse mapper row first (and the `Discount`/`Product` rows it produced — reset their `discount_temp` rows to unprocessed) so the specific strings get their own mapper rows.

### 4. Refresh cache

- `discounts:process` wraps discount creation in `Discount::withoutEvents()`, so it does **not** bump the versioned discount cache (`App\Support\CacheVersion`, group `discounts`) or sync to Meilisearch. Run `sail artisan cache:clear-discounts` after processing or the frontend will keep showing stale counts. Meilisearch sync (`discounts:index-meilisearch`, `products:index-meilisearch`, then `keywords:map-products` and `keywords:refresh-counts`) runs in `FinalizeScrapedStoresJob` wherever `MEILISEARCH_HOST` is set, dev included; after a manual `discounts:process`, run those four yourself or keyword pages keep their old products.
- The "Geriausi pasiūlymai" strip and per-category carousels on `/akcijos/{store}`/`/leidinys/{store}` are **not** cached — they're persisted rows in `curated_deals` (`App\Services\DealPoolRefresher`), which `discounts:process` already refreshes automatically for whichever store(s) it just touched (no manual step needed for a normal run). If you ever bypass `discounts:process` and write `Discount` rows another way, run `sail artisan deal-pool:refresh --store={store}` afterward.

### 4b. Make the store's `/akcijos/{slug}` page visible

`/akcijos/{slug}` 301-redirects to `/leidinys/{slug}` unless `stores.show_discounts_page` is true (`Store::showsDiscountsPage()`; every "akcijos vs leidiniai" link, the footer store list and the sitemap read the same column). Turn it on for a new e-shop scraper store (Filament → Parduotuvės → "Rodyti akcijų puslapį", or in the store's onboarding migration). It's separate from `extract_discounts_from_flyer`, which only opts the store's flyer PDFs into Gemini discount extraction (`flyers:process-discounts`). Leave that off for stores with their own e-shop scraper. The browser caches the 301 for a day, so verify with `curl` or a fresh query string.

### 5. Store logo (this repo only)

The backend `Store` model has no logo field — logos are resolved purely by convention, `<slug>.svg` under `public/assets/stores/`, via `<x-store-logo>` and every raw `<img src="/assets/stores/{slug}.svg">` call site.

1. Add the logo file at `public/assets/stores/{slug}.svg` — filename must exactly equal the store's slug. **No fallback exists**: a missing file renders as a plain broken image, doesn't crash or hide the store. Prefer grabbing the store's real logo SVG from their own live site (check page source for an `<img>`/`<svg>` in the header brand/logo area) over inventing one; wrap a raster logo in a minimal SVG (viewBox + `<image>` data-URI) only if no vector is available, matching the pattern already used for some smaller stores' logos in that folder.
2. Verify in a browser: `/parduotuves` (store directory card + logo), `/akcijos/{slug}` (store listing, breadcrumb shows the store name not "category"), `/leidinys/{slug}` (leaflet/validity-date page).

## Keyword pages (`/{slug}`, e.g. `/vitaminas-d`)

A keyword page's products live in `keyword_page_products`, filled by `App\Services\KeywordPageProductMapper` (`keywords:map-products`): each `search_terms` entry is searched on its own in the Meilisearch `products` index (all words must match; inflections via typo tolerance on words of 5+ letters), `brands` match the product brand exactly, `exclude_terms` drop products by substring, and short words ("d", "b12") must stand alone in the name. The page grid, offer counts, home teasers and product-page keyword links all read that table, so after changing a page's terms run `sail artisan keywords:map-products --page={slug}` and `keywords:refresh-counts {slug}`. A keyword URL never 404s: a published page with no offers shows an empty state, an unpublished one 301s to its category, and no automatic job or import may set `is_published` to false (details in `docs/keyword-pages.md`, "Never 404"). New pages come from `keywords:import-manual` (default file `database/data/pharmacy-keyword-pages-2026-10.json`); details and the page list in `docs/keyword-pages.md`.

## Price-watch email notifications

Users track ("seka") a product via `<x-favorite-button>`/the price-watch modal, which just writes a `product_favorites` row — there's no separate "price watch" model. `App\Console\Commands\NotifyPriceWatchers` (`sail artisan price-watch:notify`) emails a user a digest whenever a favorited product gets a new `Discount`. Scheduled twice a day (09:00 and 17:00, production). The other subscriber emails (weekly summary, new leaflet) are described in `docs/email-notifications.md`.

- **Why a command instead of a model event**: `discounts:process` wraps `Discount::create()` in `Discount::withoutEvents()` (same reason `cache:clear-discounts`/`deal-pool:refresh` are separate explicit steps, not observers) — no `created` event ever fires for a bulk-scraped discount. This command depends only on `Discount` rows existing, so it's safe to schedule on its own cadence independent of the scraping/processing pipeline's timing.
- **"New" = anti-join, not a timestamp cutoff.** `price_watch_notifications` (`user_id`, `product_id`, `discount_id`, `notified_price`, `sent_at`) records every (user, discount) pair already emailed. A pending discount is one with no matching row — so a late or skipped run still catches everything it missed next time, and nothing already-notified is ever re-sent even if this command runs again before that discount expires.
- **Same product, multiple stores → one row, not one per store.** A favorited product can have several simultaneous `Discount` rows (one per store selling it). These get grouped by `product_id`; the email shows the product once at its cheapest current offer, with every other store's price listed underneath. Every underlying discount in the group still gets a `price_watch_notifications` row (all stamped with the group's cheapest price as `notified_price`) so none of them re-trigger later, even the non-cheapest ones.
- **Re-verify discount validity at send time, don't trust the row's mere existence.** `discounts:archive-expired` only runs as part of whichever store's own processing job just touched it (`FinalizeScrapedStoresJob`) — not a standalone sweep — so an already-expired `Discount` row (`end_at` in the past) can sit in the table for a while before archiving deletes it. The pending-discounts query re-checks `start_at`/`end_at` against `now()` fresh on every run, so a discount that expires while queued (e.g. rate-limited, see below) automatically drops out and is never emailed.
- **Rate limiting — two independent rules, checked in this order:**
  1. **Hard daily cap**: a user already emailed today (`sent_at` on today's calendar date) never gets a second email today, full stop — no bypass. Still-pending items just roll forward to tomorrow.
  2. **48h "nothing new" cooldown** (`MIN_HOURS_BETWEEN_EMAILS`): otherwise, a user emailed within the last 48h is skipped *unless* at least one pending product is a **genuine price drop** — its price is lower than `notified_price` from the last time this user was told about *that specific product* (or it's the first-ever notification for it, which always counts as a drop). A genuine drop bypasses the 48h cooldown for the *entire* pending batch — i.e. a same-price item can still ride along in the email early if some other unrelated product in the same batch genuinely dropped.
  - Either way, a rate-limited user's pending (user, discount) pairs are **never** marked notified — nothing is lost, it all rolls into whichever future run is eligible, arriving as one bigger digest.
- **Auto-login, but only one link per email, not one per product.** Viewing a product needs no login — only managing favorites does — so the email carries a single magic-login link (extends `magic_login_links` with a `redirect_to` column, honored by `AuthController::redirectAfterAuth`) behind one "Peržiūrėti sekamas prekes" CTA that lands on `/favorites`. Individual product rows link straight to their own plain public product page.
- Testing locally: `.env`'s `MAIL_HOST=mailhog` means `Mail::to(...)->send(...)` never leaves the Docker network — safe to run this command for real against real local users' data and inspect the result at `http://localhost:8026` (this checkout's Mailhog), no need to mock anything.

## Product image caching (`products:cache-images`)

Re-serves hotlinked store-CDN `image_url`s from local storage (`app/Console/Commands/CacheProductImages.php`), scheduled every 5 min in production. Backoff for a failed download lives in `image_cache_failed_at` on `products` — **this column must stay in `Product::$fillable`**; it silently no-ops via mass-assignment protection otherwise (happened 2026-09-11 — the backoff never persisted, so every run re-attempted the same lowest-ID dead links forever instead of moving on, and only ~5k of ~50k hotlinked products got cached over two days as a result).

- **Self-heal via `discounts:process`**: when an existing product has `image_cache_failed_at` set and a new `discount_temp` row (any store, matched by EAN/name) brings a *different*, external (`http...`, not our own `app.url`) `image_url`, `processTempDiscount()` swaps it in and clears `image_cache_failed_at`, so the next cache-images run retries immediately. Same URL is left alone on purpose — clearing the flag would just undo the backoff for forever-failing links like barbora.lt.
- **`cdn.barbora.lt` blocks our HTTP client at the TLS/connection-fingerprint level, not by header or IP.** Confirmed live: the exact same URL returns `403 AccessDenied` from `curl`/Guzzle (tried from both the prod server and a residential Lithuanian IP, with a full realistic header set — UA, Referer, Accept, Sec-Fetch-*, HTTP/2) but `200 OK` from a real Chrome browser (via Claude-in-Chrome network inspection) hitting the identical URL. So a plain header-spoofing fix won't work here — bypassing it for real would need a genuine browser TLS handshake (e.g. a Puppeteer-based fetch, same stealth approach `scrapers/*.js` already uses), which hasn't been built.
